# Core numeric expression parity

Core IR expression execution must accept I64/I64, finite F64/F64 and mixed operands in either order for Add, Sub, Mul, Div, Gt, Gte, Lt and Lte. Integer-only arithmetic stays checked I64; floating arithmetic returns finite F64; ordered comparisons return Bool. Preserve variant-sensitive Eq and NotEq. Keep existing typed overflow, division-by-zero, non-finite and type mismatch failures rather than panic, truncation or default values.

Parse stack values into an explicit numeric case at the calculation boundary if that simplifies dispatch; use existing domain IDs, bounded expression stack and CoreError. No core dependency on vb_expr. Reuse existing stack and checked numeric helpers; i64 promotion must allocate nothing and use safe conversion without as casts. Pure calculations only; keep data, calculations and side effects distinct. No new public API, serialized change, dependency or suppressions. Scope is vb_core engine/expr_eval numeric operators and registered public evaluator tests. Keep production files below source-length limit.

Registered scenarios exercise public eval_expr_with_store and drive EvalExpr through an actual validated CompiledWorkflow, comparing result and taint for every operator and numeric pairing, negative and zero inputs, I64 min/max and exact/rounding boundaries, finite overflow, zero division and nonnumeric values. Add non-trivial numeric properties using installed proptest with symbolic ranges and independent expected values. Demonstrate old implementation fails new positive cases, then scoped pinned nextest, canonical strict source clippy and formatting. Parent Sol performs independent CODE and TEST reviews. Replay parity is separately owned by vb-eirmk.6 and must consume the shared production semantics.
