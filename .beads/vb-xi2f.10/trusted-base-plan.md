## 2. Trusted Base Ledger Entries

### TBL-001: Rust Compiler Const-Eval Engine

| Field | Value |
|-------|-------|
| **ID** | TBL-001 |
| **Trusted Kind** | `external_body` |
| **Scope** | All Kani obligations that depend on const evaluation of CODE_REGISTRY and const assertions |
| **Impact** | ALL Kani PO-001–PO-015 |
| **Reason** | CODE_REGISTRY is declared as `const &[CodeEntry]` and all uniqueness/non-zero/category assertions execute at compile time via Rust's const-eval engine. If the const-eval engine has bugs, registered invariants may be silently violated. |
| **Behavior Affecting** | true |
| **Compensating Evidence** | Runtime proptest PO-023 provides defense-in-depth by re-verifying registry invariants at test time. Rust const-eval is well-tested and used widely across the ecosystem. |
| **Owner** | proof-planner |
| **Expiry** | None (Rust toolchain lifecycle) |

| Field | Value |

| **Expiry** | None (serde is a stable ecosystem dependency) |

### TBL-004: Kani Allocator Stubs

| Field | Value |
|-------|-------|
| **ID** | TBL-004 |
| **Trusted Kind** | `stub` |
| **Scope** | PO-007 (zero-allocation proof) |
| **Impact** | PS-010 (zero-allocation) — non-behavior performance invariant |
| **Reason** | Kani alloc stubs intercept calls to `alloc::alloc::alloc`, `Box::new`, `Vec::new`, `String::new` etc. The stubs may not capture all indirect allocation paths (e.g., Display trait format strings using the std::fmt infrastructure). |
| **Behavior Affecting** | false |
| **Compensating Evidence** | Static analysis: SymbolicCode is Copy (repr(transparent) over &'static str). DiagnosticCode is Copy (repr(transparent) over u16). Display uses write! with stack-allocated buffer. No String/Vec/Box types appear in hot path. |
| **Owner** | proof-planner |
| **Expiry** | 2026-12-31 (re-evaluate if Kani stubbing improves) |

| JSON deserialization fuzz payload: max 4096 bytes | PO-022 | Standard serde JSON payload size. Diagnostic codes are < 100 bytes; 4096 provides >40x margin. |
