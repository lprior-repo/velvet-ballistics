1: # Contract Error Precedence Addendum (vb-rcizj)
2: 
3: This addendum documents the actual production error precedence in the shard
4: lifecycle command handlers. The original contract incorrectly assumed that
5: attempt-related errors (StaleAttempt, AttemptBeyondMax) would be returned for
6: forged tickets. The actual behavior checks ticket ownership/identity FIRST,
7: before any attempt validation.
8: 
9: ## Production Validation Order
10: 
11: ### For ActionCompleted (handle_action_completion, lifecycle/chunk_001.rs:568)
12: 
13: 1. **require_pending_action_ownership(ticket)** — lifecycle/chunk_004.rs:37
14:    - If run does not exist → `RunNotFound`
15:    - If run exists but no pending ticket → `InvalidActionCompletion`
16:    - If run exists but pending ticket ≠ incoming ticket → `InvalidActionCompletion`
17:    - Only passes when exact ticket match: run, step, action, attempt, capacity, seq, idempotency_key
18: 
19: 2. **run_state_get(run)** — retrieves run state (fails if run disappeared)
20: 
21: 3. **preflight_action_completion(state, ticket, output)** — lifecycle/chunk_003_chunks/chunk_001_preflight_completion.rs:59
22:    - validate_action_completion(state, ticket) → calls validate_ticket_attempt
23:    - validate_ticket_attempt (helpers.rs:118) checks:
24:      - attempt=0 or capacity=0 or attempt > capacity → `AttemptBeyondMax`
25:      - attempt < current counter → `StaleAttempt`
26:      - attempt > current counter → `InvalidActionCompletion` (future attempt)
27:    - reject_invalid_ticket_key
28:    - Output slot, taint, size, and contract validation
29: 
30: ### For ActionFailed (handle_action_failure, lifecycle/chunk_001.rs:651)
31: 
32: Identical ordering: ownership check first, then preflight validation.
33: 
34: ## Implications for Testing
35: 
36: - **Wrong run/step/action identity** → `InvalidActionCompletion` (or `RunNotFound` if run missing)
37:   - NOT `StaleAttempt` or `AttemptBeyondMax`
38: - **Capacity=0 or attempt=0 with correct identity** → `AttemptBeyondMax` (after ownership passes)
39: - **Stale attempt with correct identity** → `StaleAttempt` (after ownership passes)
40: - **Future attempt with correct identity** → `InvalidActionCompletion` (after ownership passes)
41: 
42: ## Source Evidence
43: 
44: - `require_pending_action_ownership` in lifecycle/chunk_004.rs:37-44
45: - `validate_ticket_attempt` in helpers.rs:118-138
46: - Command handling in lifecycle/chunk_001.rs:568, 651
47: 
48: ## Master Plan Alignment
49: 
50: Master plan §72 mandates `StaleAttempt` only for actual stale attempts with
51: matching identity. This addendum preserves all pre-existing behavior and old
52: assertions; it corrects the contract's expectation about forged tickets.
53: 
54: ## Additional Finding: Attempt/Capacity Validation Order
55: 
56: Production validates ticket ownership (exact match) BEFORE attempt/capacity
57: validation. This means:
58: 
59: - Forged tickets with attempt=0 → `InvalidActionCompletion` (ownership fails first)
60: - Forged tickets with capacity=0 → `InvalidActionCompletion` (ownership fails first)
61: - Forged tickets with attempt > capacity → `InvalidActionCompletion` (ownership fails first)
62: 
63: `AttemptBeyondMax` is only returned for tickets that PASS ownership validation
64: (exact pending ticket match) but have invalid attempt/capacity values. This
65: scenario requires the exact same run/step/action/seq/idempotency_key as the
66: pending ticket, differing only in attempt or capacity.
67: 
68: This means the contract's assertion that "a ticket with attempt=0 must be
69: rejected with AttemptBeyondMax" is only true for the exact pending ticket with
70: attempt=0, not for any forged ticket with attempt=0.
