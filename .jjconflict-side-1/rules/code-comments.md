# Comment policy

Read this when writing or reviewing comments, or cleaning up a file's comment style. The always-loaded core carries the baseline (names over comments; remaining comments short, only for non-obvious intent); this module covers what the core leaves out. A comment-only cleanup pass over existing files also reads `rules/comment-pass.md`: what such a pass never changes and how it proves it changed nothing.

Everything here governs comment text in every language and file format: line comments (`//`, `#`, `--`, `;`, `%`, `REM`), block comments (`/* */`, `<!-- -->`, `{- -}`, `(* *)`), doc comments and docstrings (`/** */`, `///`, `"""`), and comments in shell scripts, config and build files (e.g. YAML, TOML, INI, `.jsonc`, Dockerfile, Makefile). The `//` in the examples below stands for whichever marker the file uses. None of it touches string literals, template-literal contents, regexes, selectors, CSS values, test titles, assertion messages, fixture values, or any config value — a phrase that breaks a rule below stays exactly as it is inside a string. Rendered user-facing text keeps its own typography (`rules/frontend-design.md`).

## What survives

- The code is authoritative. A comment earns its line only where the logic cannot be traced without it: a non-obvious why, a platform or third-party quirk, an invariant, a safety boundary.
- Delete on sight: restatement of the code or narration of control flow ("check if...", "loop through..."), "this function..." / "this component..." where the name already says it, a doc comment or docstring that repeats the signature, step narration inside tests (the test title carries it), any comment defending or praising the design, a bare section label (`// Executor.`) and its ruled forms (`// --- the issuer key`, `// === HTTP`), which a blank line before the block already does without a line of text, and a cross-reference that resolves to nothing — a deleted planning doc, a dead item number. A comment documenting temporary debugging leaves with the scaffold it describes; where it is a TODO or FIXME, flag it and leave it standing.
- The marker on an intentional simplification survives: a comment naming the known ceiling and the upgrade path ("naive linear scan, index it if the list outgrows a page") is a required annotation, not a comment defending the design (core Coding rule).
- A block over 2 lines is a condense candidate: ask what it tells a reader that the code does not, keep that in 1-2 lines, drop the scene-setting, the history lesson, and the enumerated rejected alternatives. Knowledge that cannot be re-derived from the code — a browser behavior, the reason a workaround exists — survives as one sentence.
- Every checkable claim is verified against the code before it is written or reworded, and a claim you have not confirmed is never written. A redundant comment is noise; a stale one is a lie, and the stale ones a pass uncovers are its most valuable output.
- Name code after the observable role or contract it owns (`apiFetch`, `buildVoteRequestBody`, `retryVoteOrDropAfterLimit`) rather than private infrastructure, implementation mechanics, or internal processing steps.
- Record load-bearing invariants on the type or contract, not only in prose: annotate the field or parameter that must hold the constraint (`// must be square (w === h) for seamless tiling`) where a consumer sees it, so the invariant travels with the code that depends on it.
- In public repos, no comment describes private backend behavior, request-processing internals, abuse-prevention mechanics, operational topology, hidden threat-model assumptions, or how a payload is handled after it leaves the client. The calls and data shapes the public code already shows are not the concern; a comment adding internal detail on top of them is. A deliberately vague comment stays vague, and a reword never introduces a private repo name, auth mechanics, or a live third-party URL or handle.
- When touching existing files, leave the comment style better than you found it: remove obsolete or over-specific comments in the edited area, and rename a helper or local variable when that is the cleaner way to preserve readability.

## How a comment reads

- No mirrored "X, not Y" contrast, and none of its disguises ("X rather than Y", "X instead of Y"). Negative parallelism is the strongest fingerprint of machine writing: state the fact, and where the rejected alternative carries the reason, give it its own clause. `// Rendered from routes, not a second hand-ordered list: the key handler walks the same array` → `// Rendered from routes, the same array the key handler walks, so the arrow keys land on the neighboring item`. "rather than" leaves comment text in every sense, not only the mirrored one: `// jsonb_to_recordset rather than the multi-array unnest shape` and `// Written at enqueue rather than derived at send time` both go, because the shape that shipped is the one in the code and the reader needs no tour of the other — `// jsonb_to_recordset takes the enrichment rows as one JSON array` and `// Written at enqueue, so every retry sends the key the first attempt sent`. Keep a single negative that is itself the rule ("the sender's site must not be trusted"), a list of separate absent signals ("no aria-pressed, no star form"), and plain descriptive English where nothing is being contrasted.
- A contrast used as an opening frame is deleted, never rewritten: the sentences behind it already carry the point, and the frame spends a clause announcing them. `// Four typecheck configurations run, not one: the end-to-end specs and the build scripts have their own, so a dropped export fails where the main one never looks` → `// The end-to-end specs and the build scripts carry their own typecheck configuration, so a dropped export fails where the main one never looks`, and an opener promising a disclosure (`// One thing worth naming rather than hiding: with library checking turned off`) goes with nothing put in its place. Where the rejected half carries nothing the reader can act on, it goes and the sentence keeps its verb: `// Each claim was re-derived rather than reworded` → `// Each claim was re-derived`; `// run against the current tree rather than the stale base` → `// run against the current tree`.
- No stacked negation — a meaning the reader assembles from two negatives. `// Nothing may enter the queue without an owner` → `// Every queue entry carries an owner`. Watch for "not ... not-", "not ... un-", "never ... without", "no ... unless", "must not fail to".
- No borrowed diction: the ceremonial verb where the plain one exists. `// Honored up to the ceiling above` → `// Applied up to the ceiling above`; `// minted once, kept for the process lifetime` → `// generated once, kept for the process lifetime`. These are the words a model reaches for when it describes code; a developer writing the same comment uses the plain verb. A comment is plain spoken English, the register that developer would use explaining the line at a desk, so the literary abstraction goes with the ceremonial verb: `// The substance here is that the retry reuses the first key` → `// The retry reuses the first key`. The entries and their replacements are in Vocabulary below, and that list is the recurring offenders instead of the boundary — a word you would not say aloud goes whether it is listed or not.
- No padding or hedging words (Vocabulary below). Delete them; if deleting changes the meaning, rewrite so the meaning sits in the verb. Keep "just" and "only" where they carry a real restriction ("only the last read counts") or a real time reference ("the button that just vanished").
- No word claiming a choice was intended — the same words `rules/markdown.md` bans in a document, here in comment text. Only the reason proves intent, so where it follows the word is already redundant, and where none can be given the sentence is a comment defending the design and goes. `// One answer for every reject reason, deliberately. Naming the failed check tells an attacker which half of the credential was right` → `// Naming the failed check would tell an attacker which half of the credential was right, so every reject reason gets the same answer`. The plain adverb about something the code did not choose stays ("the platform drops these frames by design").
- No hedging prefix in front of a sentence (Vocabulary below). Delete the prefix and let the sentence start with its own subject. Where "best-effort" is a real mid-sentence predicate, say it in plain words ("these headers are optional").
- No label-then-explanation opener: a fragment, a colon, then the sentence that says what the fragment meant. The fragment is a verdict the reader cannot check until the rest arrives, and the rest then repeats it, so the comment says its one thing twice and starts with the unreadable half. `// Stable across retries either way: the stored key for rows written since enqueue started stamping one, the id+ts derivation for older rows` → `// Rows written since enqueue started stamping a key reuse it, older rows re-derive it from id and timestamp, so a retry sends what the first attempt sent`. The same shape wearing a place instead of a verdict: an opener justifying where the line sits (`// Validated here rather than where it is consumed: the override feeds both the compiled bundle and the manifest`). The reader can see where the comment is; open with the fact the code cannot show — `// The override feeds both the compiled bundle and the manifest, and a value only one of them parses puts them on different origins with the build still green`. A colon stays where it introduces a list, and where the half in front of it is a complete statement the reader can act on without reading further.
- A semicolon joining two independent statements becomes two sentences — joined, they read as one thought instead of two. Keep one only between list items that already contain commas.
- A list inside a comment block keeps the block's own left margin: the comment marker (`// `, `# `), then the `-` or `1.`, with each continuation line starting in the marker's column. No spaces are added to hang the items under the sentence above — the marker already says the line is an item, and the indentation drifts the first time a line is rewrapped.
- No suffix glued to a searchable name: a file, function, variable, constant, type, CSS class or custom property appears verbatim so it can be pasted straight into a search. `// ci.yml's check job` → `// the check job in ci.yml`; `// getSettings' resolved value` → `// the resolved value of getSettings`. Both apostrophe forms count, including the bare apostrophe a name ending in s takes, and so does an ending welded on without one — a plural, a verb form, a participle (`// The same backoff signInThroughAuthPages take` → `// The same backoff the loop in signInThroughAuthPage takes`). A search for the name has to hit the comment, and one added letter is enough to miss it. A platform, service or vendor name takes none either, because it qualifies the thing behind it the way that site's own documentation writes it: `// X's data-testid and GitHub's star-form action` → `// X data-testid and GitHub star-form action`. A possessive on an ordinary word or an acronym is fine.
- No abbreviations, since an unfamiliar one forces the reader to expand it before the sentence makes sense: spell them out (param → parameter, prod → production, esp. → especially). Standard industry acronyms stay (DOM, API, HTTP, URL, CSS, HTML, SVG, JSON, UI, OS, TTL, OTP, SPA, WCAG), as do ISO locale codes and established repo vocabulary.
- No number that mirrors a value the code declares: it goes stale silently and nothing fails. `// Drop entries no run has touched in 24h` → `// Drop entries no run has touched within ENTRY_TTL_MS`. A length, duration or ratio a stylesheet or a sibling module declares mirrors it the same way, units and all: `// the max(18em, ...) width floor and the max-height: 28em picker.css declares` and `// a segmented control spells its rounded end at either position (18px 0 0 18px and 0px 18px 18px 0px are the same shape)` name the declaration instead — `// the width floor and the picker height picker.css declares`, `// the whole shorthand is read because a segmented control can spell its rounded end at either end of it`. Same for a count the reader gets from the array right below the comment ("26 shipped locales", "all 8 fallback selectors") and for a count in prose ("the four first-run steps" → "the first-run steps"). An identifier is not a mirrored number: the human-readable version beside a pinned commit SHA is the only place a reader can see which release was pinned (`rules/ci-cd-security.md`).
- No measured figures — CPU percentages, memory and heap numbers, latency and duration observations, sizes read off a live page, counts of what one run observed, and the provenance stamps that carry them ("measured live", "verified on Windows 10 / Chrome 152"). One machine on one day cannot be re-derived and nothing fails when it drifts, so the measurement goes and the claim it supported stays: `// eight idle triggers cost 17.5% of one core against 0.1% with the spin off` → `// The idle animation is this page's most expensive background cost`. Keep what is not a measurement: protocol and specification constants the code must match (HTTP status codes, a contrast requirement, a storage quota), documented defaults of the tools in use, platform version floors, a CSS value the commented line itself holds as a literal, arithmetic derived from what the code declares, any value that is the literal subject of the data or the test, and the stamp on a value that must be re-tuned as hardware or a threat model moves — a password hashing cost factor carries when it was last tuned, because that date is the condition for re-tuning it (`rules/crypto.md`).
- No selector, class name or literal copied out of another file. Name the symbol that holds it — the constant, the exported class-name binding, the stylesheet — so a rename moves the comment with it: ``// there: picker.css `.ring` `` → `// there: the ring class picker.css styles`; ``// Must equal the track count of `.grid` in picker.css`` → `// Must equal the grid track count picker.css declares`. Where nothing holds the value, extract the constant instead of pinning the literal in prose. The verbatim rule above governs a name this code declares and a reader will search for; a string that lives in another file and has no binding here is the drift case.
- No numbered spec citations: drop "(WCAG 1.4.10 / 1.4.12)" and its inline forms, including inside doc comments. Keep a non-numbered mention that names something real, such as a rule-tag set an accessibility scanner accepts, and keep every identifier that resolves to a record — a CVE beside a version pin, an issue or ticket number, an RFC — because it is a pointer to the reason, not a citation of a spec version (`rules/dependencies.md`).
- No parenthesis the sentence reads better without, and no parenthetical identifier the prose already named — either one asks the reader to pause for something the sentence didn't need. Keep a real aside the sentence cannot absorb, an example it needs ("327 555" → "327K"), and a cross-reference that tells the reader where to look.
- Typography is keyboard characters, the set a developer reaches without a character picker, an Alt code or a compose key: `a-z`, `A-Z`, `0-9` and `` !@#$%^&*()_+-=`~[]{}|\:;"'<>,.?/ ``. Everything outside it is rewritten inside it: superscript and subscript digits (`// O(n²) on the unsorted path` → `// O(n^2) on the unsorted path`, `m³` → `m3`), `≤` `≥` `≠` `≈` `×` `÷` `±` (spell the comparison out), `°` `µ` `§` `†` `‰` `½`, box-drawing and block characters, and letters from an alphabet the code around the comment does not itself use. Em and en dash become a plain hyphen or a reword, an ellipsis character becomes three dots, curly quotes become straight, arrows and bullets become a hyphen or a plain word, NBSP and ZWSP become a normal space or go. A stray emoji is deleted; a glyph that is the data the comment documents stays.
- Do not over-compress. A comment that points somewhere must still say what is there, and the clause naming which half of a contract a line covers, or why a timeout has the value it has, is load-bearing. An "after" that reads as a sentence fragment or a bare "see X" was cut too far — give it back its subject. Wording that only parses if the reader is counting ("a fifth tab") reads better generically ("a new tab").

## Vocabulary

The word-level lists this module owns. They bind comment text, the prose of a commit message, and a pull request description and review comment (`rules/code-review.md`); a document's own prose is governed by the blocklist in `rules/markdown.md`, and a word that binds in both places lives there and is cited from here. Borrowed diction runs the other way: it lives here and binds a document's prose too (`rules/markdown.md`). Nothing else in this repository keeps a second copy.

- Padding and hedging: simply, merely, just as filler, actually, essentially, effectively, basically, really, so far, for now, at this point, in practice, in fact, of course, that said, as such, somewhat, quite, arguably, presumably.
- Hedging prefixes: `Best-effort:`, `Note:`, `Caveat:`, `Heads-up:`, `For safety:`, `In short:`, `Rule of thumb:`, `Sanity check:`.
- Borrowed diction, each with the plain word it displaces: honored (applied, enforced), mint in every form — mints, minted, minting (creates, generates, issues: `// The OTP alone mints a session for any address on that domain` → `// The OTP alone opens a session for any address on that domain`), verbatim (unchanged, exactly), substance in every frame that stands in front of the fact — "the substance here is", "the substance of the change" (state the fact: `// The substance here is that the token is verified twice` → `// The token is verified twice`), figurative beat (name the thing the two places share: `// Same beat as in setPopupCheckbox` → `// The write goes to storage and comes back as an event here too, as in setPopupCheckbox`), figurative slack (name the margin and what it is measured in, or say that the threshold is provisional and what would settle it). The comparative verb ("batching beats a loop of round-trips") and the product name are different words and stay.
- Banned connector: "rather than" anywhere on the surfaces this list binds, by the contrast rule in How a comment reads.
- Claimed intent: deliberately, intentionally, on purpose, by design, "this is not a bug" — listed in `rules/markdown.md`, and binding here too.
