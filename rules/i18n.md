# Internationalization

Read this when the project renders user-facing text in more than one language or locale — message catalogs, plurals, formatting, RTL.

- Never build a sentence by concatenating fragments: word order differs across languages, so every user-facing string is one catalog entry with named placeholders (`"{count} files in {folder}"`), translated whole.
- Plurals go through the catalog's plural rules (ICU plural/select, gettext forms) — languages have up to six plural categories; an `n === 1 ? "file" : "files"` ternary is wrong in most of them.
- Strings live in catalogs under stable keys and are extracted mechanically; a hardcoded user-facing string is invisible to translators and to the completeness check.
- Format dates, numbers, currency, and lists with the platform's locale API (`Intl.*` or the ecosystem equivalent), never by hand — that bakes in one locale's separators and ordering (`rules/frontend-design.md`).
- Store timestamps in UTC, render in the viewer's timezone — locale and timezone are independent inputs.
- RTL is layout, not translation: logical properties (start/end) instead of left/right, and at least one RTL locale tested before claiming i18n support.
- Sort and compare user-visible text with locale-aware collation — byte order misplaces accented and non-Latin entries.
- Translations expand (German runs ~35% longer) and fixed-width layouts truncate: flag tight-width strings to translators, and pseudo-localize in CI so clipping surfaces before a real translation does.
- Locale negotiation is one explicit fallback chain (requested → base language → default) decided once, not per call-site, so every surface falls back the same way; missing keys render marked in development and fall back silently in production.
