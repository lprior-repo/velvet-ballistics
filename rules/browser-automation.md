# Driving a real browser

Read this when automating a live browser through any automation driver or a DevTools protocol session, or testing a browser extension. The traps below produce confident wrong readings rather than errors, which is what makes them expensive.

- Prefer reading the DOM over reading a screenshot. An image tells you something looks wrong; a query tells you which node, which attribute and which computed value, and it is what the assertion should rest on.
- Keep screenshots for the human who will look at the failure.
- Open shadow roots do not answer `document.querySelector`. A component that mounts inside one reports as absent, and "the element never mounted" is the most common false reading in this whole file. Walk into every `shadowRoot` recursively when you query from an evaluate call.
- Some drivers pierce open shadow DOM in their own selector engine (e.g. Playwright locators), so a driver-side selector can succeed where the in-page query failed — know which side of that boundary each line of your script runs on.
- Synthetic events are not trusted events: `el.click()` from an evaluate call is ignored by frameworks that check `isTrusted` or listen on pointer events. Click and type through the driver. Where the driver's coordinate math is unreliable, drive the keyboard instead (focus, then Space or Enter).
- CSS `zoom` breaks coordinate mapping: the driver computes a point the browser then scales, and the click lands somewhere else.
- CSS `zoom` also splits the two measurements you are about to compare — `getBoundingClientRect` is in the zoomed space while `window.innerWidth` is not, so normalize by the factor before asserting anything is on screen.
- Setting `documentElement.style.zoom` fires no `resize` event, so nothing that listens for one will react.
- A single-page app re-renders and destroys the JS context underneath you ("Execution context was destroyed"). Element handles and evaluated references do not survive it: wait for the navigation to settle, then query again from scratch. The same applies after closing a modal or going back.
- Viewport size decides what exists. Content mounted by an `IntersectionObserver` or a lazy loader is genuinely absent below the fold, so a short window manufactures "missing element" failures. Resize to a realistic height before judging absence.
- `window.scrollTo` is a no-op on pages that scroll an inner container. Find the element that actually scrolls (`document.scrollingElement`, or the overflow container) and scroll that one; otherwise the feed never advances and every assertion after it is about the wrong viewport.
- Never wait on a fixed sleep — wait for the condition, and write the condition so it cannot be satisfied by the state you are about to assert against. A settle helper that exits as soon as either half of "the widget is present and the placeholder is gone" holds will return in the exact situation the caller is testing for, and the failure reads as a product bug.
- Logging in by script gets the account flagged: sites treat automated credential entry as abuse, and a saved profile is often encrypted to the machine. Where a test needs a real session, attach to a browser the person already signed into (a bridge extension, a debugging port, a persisted profile they control) instead of automating the login form. Every such run touches real data on a real account — act accordingly.
- Extensions and add-ons install differently per browser and the difference is not cosmetic: Chromium takes a load-from-disk flag, Firefox installs a temporary add-on over the remote debugging protocol, and some drivers cannot navigate to or even see the extension's own pages. Establish what the driver can reach before writing tests against it, and mark the rest as a known hard limit rather than rediscovering it every few weeks.
- A network error inside the browser is frequently not the browser: a host firewall denying the child process produces a page-level failure (`ERR_NETWORK_ACCESS_DENIED` and friends) while the runner itself still has network, so the suite's own preflight passes and the failure looks like a broken test.
- Run one headed suite at a time. Two fight for CPU and manufacture flakes, and a manufactured flake costs a diagnosis rather than a rerun (`rules/shared-machine.md`, which also covers the browsers a crashed run leaves behind and the per-run profile directories that grow without bound).
