# Applied cryptography

Read this when code hashes, encrypts, signs, or generates anything security-bearing: passwords, tokens, sessions, signatures, encrypted fields.

- Never implement a primitive, a mode, or a protocol yourself. Use libsodium, the platform's audited API (`crypto` in Node.js, `cryptography` in Python, Web Crypto in browsers), or a maintained wrapper — "we only wrote the padding" is how it breaks.
- Banned in a security role: MD5 and SHA-1 (signatures, tokens, integrity), ECB mode, a static or reused IV/nonce, and any non-cryptographic RNG (`Math.random`, `rand()`, `System.currentTimeMillis` as a seed). MD5 for a cache key or file dedup is fine — the role decides, not the function.
- Passwords use argon2id (memory-hard) or bcrypt; the cost factor is a tuned number with a comment naming when it was last measured, re-tuned as hardware moves — a constant copied from a 2015 blog post is a finding. Enforce a length floor (≥12) plus a breached-password check rather than composition rules.
- bcrypt reads only the first 72 bytes of its input: two inputs sharing that prefix hash identically, and a composite input (an id plus a username plus a password) authenticates on the prefix alone — never feed bcrypt a concatenation of fields.
- Some libraries truncate the 72-byte input silently, others reject it. New systems use argon2id; with bcrypt, cap the input at 72 bytes or pre-hash as `bcrypt(base64(hmac-sha384(password, pepper)))`, since a raw digest can contain a null byte that ends the input early.
- Random values that matter (tokens, session ids, salts, nonces, reset codes) come from the CSPRNG: `crypto.randomBytes`, `secrets.token_urlsafe`, `crypto/rand`, `SecureRandom`. Name the entropy in bits when reviewing: ≥128 for anything guessable offline.
- Compare secrets, MACs, and signatures in constant time (`crypto.timingSafeEqual`, `hmac.compare_digest`, `subtle.ConstantTimeCompare`); `===` on a token is a timing oracle.
- The constant-time call is necessary, not sufficient: an early `if len(a) != len(b): return False`, a secret-dependent branch, or a lookup indexed by secret bytes leaks the same information one line above the safe compare. Never hand-roll the loop either — the optimizer is allowed to turn a branch-free source loop into a branching binary; use the vetted primitive so the guarantee survives compilation.
- Overwrite secret buffers when the operation ends, with a call the compiler may not elide (`zeroize`, `explicit_bzero`, `SecureZeroMemory`) — a plain loop over a buffer that is never read again is a dead store the optimizer deletes. In a garbage-collected runtime this is unachievable, so state the limit instead of faking it: keep the secret short-lived, never copy it into an immutable string, and keep it out of anything that gets serialized, logged, or attached to an error.
- Encrypt with an AEAD (XChaCha20-Poly1305, AES-GCM) so ciphertext is authenticated; if you ever hand-compose, it is encrypt-then-MAC, never MAC-then-encrypt. A unique nonce per message is a correctness requirement, not a suggestion.
- JWT: pin the expected algorithm on verify and reject `alg: none` and any algorithm switch (HS/RS confusion is a full auth bypass); verify `exp`, `iss`, and `aud`, not just the signature. Prefer an opaque session id over a JWT when you control both ends.
- Design key rotation in from the start: a key id travels with the ciphertext/token so old material decrypts while new material is written under the new key. A scheme with no rotation path becomes unrotatable exactly when it is compromised.
- Encrypt data at rest with envelope encryption: a KMS or HSM holds the key-encryption key and never hands it out, the service requests a per-record data key, and only the wrapped data key is stored next to the ciphertext. Rotation then re-wraps data keys instead of re-encrypting the whole table.
- Keys live in a secrets manager or env, never in source, and never in the same store as the data they protect (core Security rule).
- Store token hashes, not tokens (`rules/backend-security.md`); a leaked table then yields nothing replayable.
- TLS is the transport floor: 1.2 minimum, certificate validation never disabled "for local dev" in shared code — gate it behind an explicit local-only flag or fix the local trust store.
- Certificate pinning is a client-side control that needs a rotation path shipped before the pin, or renewal day becomes an outage; ship a backup pin with it.
- On a client device, secrets and tokens live in the OS credential store (keystore, keychain, credential manager) under the strictest access class the feature allows, never in preferences, a plain file or a local database. A local unlock (biometric, PIN) releases a key from that store; a boolean in app code is what a patched build flips.
