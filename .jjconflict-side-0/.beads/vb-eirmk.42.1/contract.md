## Normative contract

The master table at `velvet-ballistics-MASTER.md:2441-2451` defines `has(Object, Symbol) -> Bool`. Return true exactly when the valid object contains a field with the requested valid symbol key; return false when that valid key is absent, including an empty object. Resolve handles before membership so an invalid object or symbol handle is an error, not a false absence. Preserve exactly two arguments and left-to-right operand validation.

`contains` remains a separate helper with its own master contract and qualification. The current master describes unresolved `contains` parity at line 2448; do not rename the old list-membership `has` tests to `contains` or treat that as accepted coverage. A reviewer may approve separate `contains` cases only when their oracle matches its resolved contract.

## Exact evaluator error, precedence, and arity contract

Operand and handle precedence is explicit: where the API has an argument list, enforce its existing arity boundary first; then check receiver type; then key type; then resolve Object handle; then resolve Symbol handle; then test field-key membership. A receiver and key that are both wrong select receiver type mismatch. Unknown/Any receiver with a known wrong key selects key mismatch; known wrong receiver with Unknown/Any key selects receiver mismatch. For Object with an invalid handle plus a wrong-typed key, key type mismatch wins. For two correctly tagged invalid handles, Object resolution wins. Do not interleave left-handle resolution before checking the right operand type.

`vb_expr` static type checking already routes Has to `check_object_text` at `crates/vb_expr/src/expr_typecheck/helper_typecheck.rs:7-20,134-153`; it accepts Object/Text and Unknown independently and rejects known wrong types. `typecheck_helper` checks exact arity before inferring operands at `crates/vb_expr/src/expr_typecheck/mod.rs:151-172`. The public expression parser also enforces exact arity after parsing arguments. For arities 0, 1, and 3, both return `ExprError::HelperArityMismatch { helper: "has", expected: 2, actual: n }`. The positional type payloads are `TypeMismatch { expected: "object", found: "boolean" }` for Bool/Unknown and `TypeMismatch { expected: "text", found: "i64" }` for Unknown/I64. Preserve this checker and parser behavior.

The direct context-free `vb_expr::eval_helper(Has, args)` and store-aware `eval_helper_with_store(Has, args, store)` both enforce the same `HelperArityMismatch` payload before operand checks. Context-free Has checks receiver then key tags and then returns `ExprError::TypeMismatch { expected: "value-store context required for object field lookup", found: "object handle without store" }` for correctly typed arguments; it cannot validate either handle. Preserve this behavior and do not add invalid-handle errors to the context-free API. Store-aware Has checks receiver tag, key tag, resolves Object, resolves Symbol, then membership. Wrong Bool receiver and I64 key tags return `ExprError::TypeMismatch { expected: "object", found: "boolean" }` and `{ expected: "text", found: "number" }`; invalid handles return `ExprError::InvalidReference { reference: format!("object:{id:?}") }` or `format!("symbol:{id:?}")`.

For the separate `vb_compile` parser, `parse_ast` builds the AST and runs type-taint; its expression parser accepts Has arities 0/1/3 and does not own helper arity diagnostics. The type-taint Has position guard must inspect only present first and second operands and must not introduce missing/extra-argument errors. `YamlCompiler::compile` maps 0/1/3 to `CompileErrors([CompileError::ExpressionHelperArity { helper: "has", expected: 2, actual: n }])` through canonical expression type checking/lowering. `YamlCompiler::parse_ast` has no such arity boundary; keep positional validation independent so missing arguments do not invent a type error and an extra third argument is left for canonical compile to reject. Do not add an arity guard to bytecode execution.

Direct malformed `vb_expr::eval_expr_program_with_store` bytecode has no helper-arity variant: zero or one stack operands at Has returns `ExprError::StackUnderflow`; three pushed operands followed by Has leave a non-single stack and return `ExprError::StackOverflow { max: MAX_EXPRESSION_STACK }`. Core hot `eval_expr_with_store` bytecode has no helper-arity variant either: zero/one operands return `EngineError::ExpressionStackUnderflow`; three pushed operands followed by Has fail final stack validation with `EngineError::InvalidCompiledWorkflow { reason: "expression leaves non-single result" }`.

Replay private helper failures begin as `ReplayError::ExpressionEvalFailed { step: StepIdx::ZERO }`, but `eval_replay_op` remaps them to the current `run.pc()`. `eval_expr_for_replay` also reports a non-single final stack at `run.pc()`. Public replay negative cases must use a nonzero-PC frame and assert `ReplayError::ExpressionEvalFailed { step: that_pc }` for wrong types, invalid handles, underflow, and non-single stack; reserve ZERO for a direct private-helper test only. Replay's public error does not reveal which internal precedence branch failed.

For core hot and replay valid runtime operands use `EngineError::TypeMismatch { expected: "object"/"text", found: actual_type_name }` and invalid handles use `ObjectOutOfBounds { object }`/`SymbolOutOfBounds { symbol }` in core; replay maps them to the current-PC error above. A valid missing key, including in an empty object, is Bool(false), never `ObjectFieldNotFound`.

## Pinned-source findings and minimal change surface

Master `velvet-ballistics-MASTER.md:2441-2451` defines `has(Object, Symbol) -> Bool` and documents the core/replay list-membership divergence. Store-aware `vb_expr` already checks receiver/key tags and resolves Object at `crates/vb_expr/src/expr_eval/helper_store_values.rs:190-204`; it must additionally resolve the Symbol handle before key membership. Leave the valid static Has checker `check_object_text` unchanged.

The public `YamlCompiler::parse_ast` entrypoint at `crates/vb_compile/src/mod_compile_core.rs:75-90` invokes type-taint validation. Its choose-condition facts are passed as `"choose.condition"`; `type_taint_expr::helper_fact` at lines 119-129 currently merges taint and assigns Has Bool without checking operand positions. A Has-specific positional check is therefore scoped to this parse-AST/type-taint path and must preserve `ValueType::Any` as a wildcard independently per operand: Any/I64 must report expected text/found number; Boolean/Any must report expected object/found boolean. Use the passed context field (`choose.condition` for the chosen parse-AST fixture), never a globally hardcoded field. Do not add arity validation there. The exact expected error on this entrypoint is `CompileError::TypeMismatch { field: "choose.condition", expected, found }`.

Canonical `YamlCompiler::compile` is a distinct entrypoint: `canonical_types::infer_canonical_expr_type` calls the already-correct `vb_expr` checker, and `vb_expr_error_to_compile` maps operand mismatches to `CompileError::TypeMismatch { field: "set.value", expected, found }`; choose condition return-type validation separately uses `choose.branches[].when`. Keep these field conventions and its existing Known/Unknown behavior. The supported input shorthand `any` is accepted at `schema.rs:105-117`, maps to `InputSlotKind::Any` at `mod_compile_lowering/input_schema.rs:13-27`, and maps to `ExprType::Unknown` at `source_declarations.rs:133-136`; use declared Any inputs and references to them for workflow compile acceptance tests, not concrete Object/Text fixtures mislabeled as dynamic.

The bounded production alignment surface is Has-specific behavior in `crates/vb_compile/src/type_taint_expr.rs` for parse-AST positional validation, `crates/vb_expr/src/expr_eval/helper_store_values.rs` for Symbol-handle validation, `crates/vb_core/src/engine/expr_eval/ops_text_list.rs` for core hot Object/Symbol lookup, and `crates/vb_core/src/replay/helpers.rs` for replay Object/Symbol lookup. Keep `crates/vb_expr/src/expr_typecheck/helper_typecheck.rs`, canonical compile mapping, parser/lowering arity behavior, context-free helper behavior, public APIs, schemas, dependencies, and unrelated helpers unchanged. The old hot Has tests at `crates/vb_core/src/engine/expr_eval/ops_text_list/tests.rs:238-274` encode list membership and must be replaced by stronger normative Object/Symbol cases while retaining both names and registration; do not mechanically rename them to `contains`.
