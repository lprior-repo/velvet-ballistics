## Top-3 NOT-PATCHED with reason

1. **vb-2gxqo (RE-019 — runtime engine: unhandled journal events fabricated as `RunFailedEvent`)** — `chunk_002.rs:266-273` still fabricates `RunFailedEvent` for any `RuntimeJournalEvent` variant not matched by `run_storage_event`, `action_storage_event`, or `boundary_storage_event`. No error path; no `RuntimeError::UnsupportedEvent` variant; no regression test. This is a **silent corruption** bug — any future journal event added without updating all three matchers will be persisted as a fabricated run-failure, corrupting the durable event log. The fix should add a new `RuntimeError::UnsupportedEvent { event_kind: &'static str }` variant and return `Err(...)` instead of fabricating `RunFailedEvent`.

2. **vb-3a58y (ARCH-W0-11 — `reference/` at repo root violates §23)** — `reference/` is still at the repo root with `name = "reference"` and is NOT in `workspace.members`. The supposed fix commit `ef2dbf34c` exists but is not an ancestor of `main`. `cargo check -p reference` fails with "package ID specification `reference` did not match any packages", confirming it is a workspace-orphan phantom. §23 forbids this. To fix: cherry-pick `ef2dbf34c` (which moves files but does NOT update `Cargo.toml` — that step is still missing) and add `crates/vb_reference` to `workspace.members`.

3. **vb-28qw9 (SA-007 — `validate_compiled_ir_record` ignores `metadata_hash`)** — the bead's close reason cites three symbols (`validate_compiled_ir_record`, `validate_artifact_metadata_hash_binding`, `admission/record.rs:44`) that **do not exist** in the codebase, plus a `metadata_hash` field on `CompiledIrRecord` that does not exist (`records.rs:246` declares only `digest` and `ir`). This is a **phantom closure** — the bead was closed claiming a fix that was never applied (or was reverted). Either the admission/metadata code never landed, or it was rolled back. The bug remains in effect: `CompiledIrRecord` does not bind a metadata hash, so admission has no way to verify the artifact envelope metadata matches the stored bytes.

## DEEP-DIVE: where I disagree with the obvious PATCHED

- **vb-2jb1p (CW-008 Together cardinality cross-check)** — superficially PATCHED, and the gate-11 fix in `vb_validate/src/gates.rs:618-659` does correctly enforce `branches.len() == branch_count` and `branches[branch] == index`. **However:** the test surface (`gate_tests.rs:419, 589, 617`) covers three cases — valid TogetherStart/Join, orphan TogetherBranch, and TogetherJoin with mismatched `branch_count` — but **never tests `TogetherBranch.branch = N` where N is out-of-range for the TogetherStart, or where two TogetherBranches share the same `branch` id**. The `require_matching_together_branch` predicate at gates.rs:630-632 only fires if the target step matches; an out-of-range `branch` would simply have no matching `branches[i]` and the check passes silently. The fix is correct for the headline bug, but the matching-target-only predicate misses the `branch >= branches.len()` and `branch` collision cases. Recommend adding two regression tests:
  - `gate_11_rejects_together_branch_id_out_of_range` (TogetherBranch.branch = 99 when TogetherStart has 2 branches)
  - `gate_11_rejects_together_branch_id_duplicate` (two TogetherBranch nodes with branch = 0)
