## Weak-test cases (top-3)

1. **vb-hm0b7 (RS-003 IdempotencyTracker `order` Vec)** — every existing test asserts only `tracker.len()` ≤ capacity (the `completed` map). The literal defect ("`order` Vec grows unboundedly while `completed` stays bounded") is not pinned; the cursor-based eviction only constrains `completed`, not `order`. A 1-line mutation that drops `order` from eviction (or lets it grow unboundedly) would still pass `idempotency_tracker_eviction_oldest_removed`, `idempotency_tracker_capacity_one_evicts_on_second_insert`, and `prop_length_never_exceeds_capacity`.

2. **vb-goqvb (SR-012 `decode_snapshot_slots` O(N·M))** — the fix replaces the per-slot linear scan with a `HashMap` (see `hydrate_support.rs:167-170`), but the regression test (`hydrate_run_frame_taint_preserved_when_tail_has_no_taint`) verifies only merged-taint correctness. A revert to the inner-loop lookup would still produce the correct entries; there is no timing/iteration-count assertion.

3. **vb-ia6i4 (RS-108 lifecycle counters add cumulative executed steps repeatedly)** — production uses `add_steps` with a CAS+saturating loop (`counters.rs:49-63`) and the per-shard `steps_total` aggregation also uses `saturating_add` (`runtime.rs:460`), but no test simulates the original "counter add twice" defect across multiple run lifecycles. The existing saturating-add tests are zero-identity and commutative, not the original defect scenario.
