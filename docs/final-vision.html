Velvet-BallisticsFinal Vision

The Machine That Builds the Machine

Velvet-Ballistics is the adaptive software layer for building the best internal development platform: an AI-native compiler and durable runtime that turns proposed automation into verified, bounded, replayable, policy-governed artifacts.

The product promise: AI can propose automation, but only Velvet decides what becomes real.

The long-term ambition is not another workflow runner, CI wrapper, or agent chat surface. The ambition is a machine that writes, verifies, operates, observes, and improves the automation that builds the internal development platform itself. It is the machine that builds the machine.

That machine must be adaptive, but not self-modifying in the dangerous sense. It adapts by evidence. It records what happened, explains why a decision was made, emits incidents when its current artifact is insufficient, and feeds those incidents back into a new verify → compile → accept cycle.

Swamp provides the useful pattern: typed agent-facing authoring, explicit runtime knowledge, review before production, and governed execution. Velvet hardens that pattern with accepted artifacts, numeric IR, replayable journals, idempotency checks, capability gates, and NASA/JPL-style Rust discipline.

North star: Velvet is adaptive automation for internal platforms where every new behavior crosses a compiler boundary before it can run.

GoalInternal Development Platform

1. The Platform We Are Building

The best internal development platform is not a pile of dashboards. It is an operating system for engineering work. It gives teams safe defaults, fast feedback, repeatable delivery, known failure modes, and trustworthy automation that does not surprise operators at 3 AM.

Velvet’s role is to become the compiler-enforced automation plane for that platform. It should help AI and humans author platform workflows, but it should not trust either of them blindly. It should verify intent, reject unsafe plans, produce accepted artifacts, execute them durably, and report evidence back to the platform.

The platform provides

  • golden paths for build, test, release, deploy, and rollback;
  • artifact provenance and policy-bound admission;
  • operator approvals and human-in-the-loop gates;
  • incident evidence, replay, and recovery guidance;
  • bounded automation that fails closed.

Velvet enforces

  • compiler acceptance before runtime execution;
  • numeric IR only in the hot path;
  • outbox/inbox effect boundaries;
  • capability grants separate from requirements;
  • idempotency and replay evidence.

In this vision, AI is not the authority. AI is a proposal engine. It drafts workflows, repairs diagnostics, summarizes incident bundles, and proposes new artifacts. Velvet is the customs office. Only accepted artifacts cross the border.

AI proposes automation
Velvet verifies automation
Accepted artifacts run
Runtime emits evidence
Evidence feeds the next proposal

PrincipleSwamp Adapted, Not Copied

2. What We Borrow From Swamp

The useful Swamp idea is not YAML, a repository data layout, or remote workers. The useful idea is control architecture for AI-authored automation: typed cold authoring, reviewable intermediate state, explicit runtime knowledge, policy-governed execution, and feedback loops that remain visible.

Velvet translates that into a stricter system. Authoring is cold. The compiler is heavy. Runtime is thin. The artifact is the trust unit. The journal is the knowledge model. Feedback does not mutate live workflow logic; it produces evidence for the next compiler cycle.

Swamp patternVelvet incarnation
Typed agent-facing automationRust SDK source model that builds inspectable workflow specs, not arbitrary execution.
Review before productionVerify, simulate, compile, and accept before runtime admission.
Runtime state as knowledgeJournal, snapshots, tickets, receipts, signal observations, and incident bundles.
Policy-governed executionAdmission and execution policy digests recorded in artifacts and journal events.
Agent productivityStructured diagnostics and repair hints; AI patches source, but cannot bypass acceptance.
Translation: Swamp makes automation explicit and reviewable. Velvet makes automation explicit, reviewable, compiled, replayable, and artifact-bound.

The boundary matters. Velvet should never become “AI runs scripts against production.” It should become “AI submits candidate automation to a compiler that has the power to say no.”

ArchitectureAdaptive Evidence Loop

3. The Adaptive Evidence Loop

The central mechanism is the Adaptive Evidence Loop. It merges Swamp’s visible automation posture with MAPE-K’s monitor, analyze, plan, execute, and knowledge separation, while preserving Velvet’s accepted-artifact boundary.

AuthorAI or human uses the Rust SDK source model to construct a workflow specification.
VerifyThe compiler checks bounds, effects, capabilities, idempotency, policy, taint, replayability, and resource contracts.
AcceptThe compiler emits an accepted artifact with source, IR, policy, SDK ABI, action ABI, and resource digests.
ExecuteThe runtime executes numeric IR only, through durable state transitions and bounded effect scheduling.
ObserveThe runtime writes journal evidence: admissions, tickets, completions, gates, signals, policy decisions, and incidents.
EvolveIncident bundles and replay evidence feed a new out-of-band proposal that must pass the compiler again.

Runtime adaptation is deliberately narrow. It may select only behavior already encoded in the accepted artifact. If no verified path exists, it emits an incident and stops, gates, or suspends. Supervisory adaptation is broad, but it is outside the runtime and mediated by the compiler.

Bounded runtime adaptation:
  observe journaled signal -> evaluate compiled guard -> select accepted branch or emit incident

Unbounded supervisory adaptation:
  incident -> AI/human proposal -> verify -> compile -> accept -> install

TrustArtifact Boundary

4. The Accepted Artifact Is the Border

The accepted artifact is the unit of trust. It is not just a compiled file. It is a knowledge capsule that records what source was accepted, which compiler and SDK ABI shaped it, which action registry it depends on, which policies governed acceptance, and which resource contracts bound execution.

ArtifactHeader:
  artifact_digest
  source_spec_digest
  ir_digest
  sdk_abi_digest
  action_abi_digest
  admission_policy_digest
  execution_policy_digest
  resource_contract_digest
  signal_schema_digest
  adaptation_envelope_digest

The runtime must independently validate the artifact at admission. It must not trust the compiler by reputation, local profile names, or filenames. Digest mismatch, unknown artifact version, stale action registry, incompatible policy, malformed IR, or missing grants are hard rejections.

Artifact admission rules

  • Runtime accepts accepted artifacts, not loose IR and not source files.
  • Policy names are labels; policy digests are the trust boundary.
  • Action requirements are not grants. Operator/runtime grants remain separate.
  • Debug maps and diagnostics are cold metadata; they cannot affect execution.
  • Old artifacts either replay under a compatibility contract or fail with explicit migration state.
Border rule: if it did not pass verify → compile → accept, it is not real to the runtime.

AuthoringRust SDK Source Model

5. Rust as Authoring Syntax, Not Runtime Logic

Velvet should dump YAML as an active authoring surface, but it must not replace YAML with arbitrary Rust workflow functions. Rust becomes the host language for constructing inspectable data. The SDK is a compiler front-end. The workflow is a specification, not a closure.

The v1 ergonomic surface should be a boring builder API. Macro syntax can come later as sugar over the same source model. This avoids making proc-macro magic the foundation of the product.

let workflow = Workflow::new(name!("deploy"))
    .input_schema::()
    .action(ActionRef::new(DB_APPLY_MIGRATION), migrate_input)
    .idempotency_key(key!(workflow_digest(), step_id(), input.change_id))
    .gate(Gate::manual("production_signoff", Timeout::minutes(30)?))
    .finish(result_expr)
    .build()?;

Forbidden in workflow semantics

  • Rust closures, callbacks, custom predicates, and trait-object workflow logic;
  • ambient I/O such as files, environment, network, process execution, or wall-clock reads;
  • runtime string lookup of action names, capability names, or policy names;
  • raw IR authoring as an escape hatch;
  • proc macros that hide control flow, allocation, panics, or side effects.

Conditions, transforms, idempotency keys, signal guards, and resource bounds must be typed AST nodes the compiler can inspect. That is how Rust authoring remains Gleam-like: friendly syntax, strict compiler, limited escape hatches, boring artifact.

EffectsOutbox, Inbox, Actions

6. Sensors and Effectors Are Durable Boundaries

MAPE-K talks about sensors and effectors. Velvet’s concrete version is outbox and inbox. The deterministic core emits bounded effect requests into a durable outbox. External completions, approvals, observations, and answers return through a durable inbox. Nothing else gets to poke the workflow state.

Outbox

Action tickets, gate openings, scheduled timers, incident emissions, and durable effect intents. Every record has sequence numbers, capability requirements, payload digests, timeout bounds, and idempotency evidence.

Inbox

Action completions, operator decisions, observed signals, timer firings, cancellation requests, and recovered receipts. Every record is deduplicated, ordered, and replayable.

Actions are manifest-first. The compiler reasons over manifests before any executor code is trusted. Executors are separate adapters that receive scoped capability tokens and durable tickets. An action manifest describes side effect class, retry safety, idempotency scope, input/output schema digests, timeout policy, secret requirements, and required capabilities.

ActionManifest:
  action_id
  side_effect
  retry_safety
  idempotency_scope
  input_schema_digest
  output_schema_digest
  required_capabilities
  timeout_policy
Effect rule: all external reality crosses through tickets and receipts, never through hidden runtime callbacks.

RuntimeBounded Adaptation

7. Runtime Knowledge and Bounded Adaptation

Velvet should use reflection in the engineering sense: the system keeps a durable model of itself. But that model is evidence, not a permission slip for self-modification. The runtime knowledge model consists of journal events, snapshots, action tickets, gate states, signal observations, policy decisions, receipts, and incident bundles.

MAPE-K roleVelvet implementationSafety rule
MonitorJournal readers, signal extractors, action receiptsObserve typed, replay-stable signals only.
AnalyzeDeterministic policy evaluatorNo LLM or text scripting in the runtime path.
PlanPreverified variant selector or incident requestChoose accepted variants only; otherwise emit incident.
ExecuteNumeric IR transitions and durable effect schedulingJournal every state change and effect intent.
KnowledgeArtifacts, policy digests, snapshots, receiptsDurable, bounded, replayable, inspectable.

Runtime policy guards, if added, must compile to numeric predicates. They may evaluate journaled observations and artifact metadata. They may not parse CEL, YAML, JSON, Rust, JavaScript, or any other source language in the hot path.

Preverified variants are allowed only when each branch has already passed compiler checks. Variant selection is a switch over accepted alternatives, not a planner. If the runtime needs behavior that is not already in the artifact, it emits an incident bundle for the supervisory loop.

AssuranceNASA/JPL and Evidence

8. Engineering Discipline Is Product Surface

The internal platform should trust Velvet because Velvet is boring where it matters. The runtime core uses bounded control flow, typed errors, checked arithmetic, explicit resource caps, no panic paths, no unchecked indexing, no lossy casts, no ignored fallible results, and no production unsafe by default.

NASA/JPL discipline is not just a code style. It is part of the product promise: Velvet rejects automation that cannot be bounded, replayed, inspected, or safely retried. The compiler performs expensive analysis before acceptance so the runtime can execute compact numeric artifacts with minimal dynamic work.

Acceptance evidence

  • Artifact golden tests for canonical serialization and digest stability.
  • Compile-fail tests for illegal SDK workflow shapes.
  • IR decoder and validator fuzzing.
  • Capability-forgery and grant-mismatch suites.
  • Crash matrix tests at every outbox/inbox boundary.
  • Replay determinism tests across runtime upgrades.
  • Incident bundle conformance and evidence rendering snapshots.
  • Strict Rust gates for no unsafe, unwrap, expect, panic, todo, unchecked indexing, unchecked arithmetic, or lossy casts in production code.
Assurance rule: absence of evidence is not approval. Missing proof, missing benchmark, missing replay, or missing policy digest is a blocker or residual risk.

The platform becomes better because the machine is forced to produce evidence every time it changes itself.

RoadmapStop at the Right Place

9. Roadmap and Final Shape

The safest roadmap strengthens trust boundaries before adding adaptive behavior. Do not start with a beautiful macro language. Start with artifact envelopes, manifest-first actions, idempotency, durable effects, and incident evidence.

  1. Trust envelope: artifact digests, SDK ABI digest, action ABI digest, policy digest, admission receipts, mismatch rejection.
  2. Effect model: manifest-first actions, capability tokens, idempotency AST, durable outbox/inbox.
  3. Evidence loop: incident bundles, replay reports, operator answers, and supervisory recompile/install tooling.
  4. Authoring model: Rust SDK source model with compile-fail tests and structured diagnostics.
  5. Bounded adaptation: journaled signals, numeric policy guards, preverified variants, gates, and incident emission.
  6. Ergonomics later: macro DSL, LSP, agent adapter, action packs, and policy packs.
Final vision: Velvet is the adaptive, compiler-enforced machine that builds the automation for building the internal development platform.

It watches the platform, records evidence, rejects unsafe proposals, accepts bounded artifacts, executes only numeric IR, and turns incidents into new compiler-mediated improvements. The system gets faster at building the machine without becoming less accountable.

That is the final product wedge: not a Temporal clone, not a DAG runner, not a YAML executor, not an agent free-for-all. Velvet is the machine that writes automation under law.

AI proposes. Velvet verifies. Accepted artifacts run. Evidence builds the next machine.
