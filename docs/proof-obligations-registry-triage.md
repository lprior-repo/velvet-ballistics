# Proof-obligations registry triage

Triage of the required-test-name gap in `contracts/proof_obligations.yaml`, named as the open follow-up by PR #326 (lane E). Evidence gathered first-hand on main `2ca6dfb9`; PR #327 changed exactly one file (`crates/workspace_tests/tests/vb_kkvb_xtask_command_shell_coverage.rs`, +22/-80, verified via the GitHub files API), which touches neither the registry nor any test cited here, so all evidence carries to `f540d372` unchanged.

## Method

The registry lists 44 required test-name mentions across its `tests:`, `property_tests:`, and `differential_tests:` fields (42 distinct names; `whole_workflow_budget_within_policy` and `test_repeat_digest_cross_path_equivalent` appear twice each). Each name was checked against every Rust `fn` identifier in the tree (`grep -rhoE 'fn [a-zA-Z0-9_]+' --include=*.rs .`), then against the compiled test binaries (`cargo test -p <crate> --lib -- --list` plus the `vb_compile` integration targets `digest_repeat_unit`, `repeat_digest_integration`, `v1_primitive_lowering`). For every name that does not resolve, the covering evidence was found by searching for the property it names, reading the candidate test, and running it. Verus files named by the L4 obligations were run first-hand (`verus --crate-type=lib`). The reference crate was checked first-hand in a scratch copy outside the workspace (its `Cargo.toml` has no `[workspace]` table and it is not a workspace member, so `cargo check` refuses it in place; the copy is byte-identical except for two `path =` lines rewritten to absolute paths).

## Disposition summary

## Genuinely missing (4)

No Rust test pins the property; the TLA model exists where noted, but the Rust test leg the registry requires does not. Each is a follow-up batch, not part of this triage.

- `journal_before_dispatch` (VB-REPLAY-001, L3): no test anywhere in the tree asserts that `ActionScheduled` is journaled before the action is dispatched — the name, and every near name (`journal_before`, `before_dispatch`, `scheduled_before`, `journaled_before`), matches zero tests in the vb_runtime lib binary (2436 tests listed), and `journal_before_dispatch` / `JournalBeforeDispatch` appears in no Rust file. The TLA model `specs/tla/JournalBeforeDispatch.tla` exists. The crash-lab leg is also missing tooling: no `crash-lab` command exists in `xtask/src/` (only the proof-level label in `xtask/src/proof.rs`).
- `single_shard_owner` (VB-REPLAY-004, L3): no test pins that a run has exactly one shard owner. The closest tests pin ownership *tracking*, not uniqueness: `run_state_insert_rejects_untracked_active_owner`, 1 passed; `pending_action_aggregate_only_tracks_active_owner`, `pending_timer_aggregate_only_tracks_active_owner`, `pending_boundary_snapshot_counts_checked_out_active_owner`. The TLA model `specs/tla/ShardOwnership.tla` exists.
- `bytecode_vs_ast` (VB-EXPR-001, L2): no differential test compares AST evaluation against bytecode evaluation on the same input. The 91 `bytecode` tests in the vb_expr lib binary assert expected values on the bytecode path only (`compile_expr_to_bytecode_roundtrips_with_eval`, 1 passed, asserts `3 + 4 * 2` evaluates to 11 through the bytecode path; `end_to_end_lex_parse_compile_eval` does the same), while the AST interpreter is tested separately in `expr_eval` tests; nothing evaluates both paths and compares. The registry command `cargo nextest run -p vb_expr bytecode_ast_equiv` matches 0 tests.
- `fjall_fsync_boundary` (VB-STORAGE-FJALL-001, L6): no test counts or asserts fsyncs. The closest tests assert persistence round-trips, not the fsync boundary: `append_strict_batch_writes_all_events_with_single_fsync`, 1 passed, but its body only appends 3 events and asserts they replay back — it never observes an fsync count; `flush_profile_batches_strict_events_into_single_fsync` is the same shape. The registry itself records Fjall fsync correctness as an externally assumed dependency, so the missing leg is a boundary-pin test, not a correctness proof.
